# Ansible cluster automation

This directory contains the Ansible automation used by the OTP Relay Kubernetes project when the deployment target is a multi-node cluster.

The Ansible layer is responsible for configuring the real server as the K3s control-plane node and joining the provisioned worker VMs as Kubernetes workers. It does not own the OTP Relay application source code, frontend source, observability dashboard source, or repository sync behavior.

---

## Layer purpose

The Ansible layer turns prepared infrastructure into a working Kubernetes cluster.

In the standard lab/dev topology:

```text
real server / localhost
  - K3s control plane
  - Ansible runner
  - Docker/image build host
  - kubectl operator host

worker1 VM
  - K3s worker node

worker2 VM
  - K3s worker node

external NFS server
  - persistent /app/data storage
```

The worker VMs are normally created by:

```text
automation/libvirt/provision-vms.sh
```

The generated inventory is written to:

```text
automation/ansible/inventory.generated.ini
```

---

## Responsibilities

This layer is responsible for:

```text
installing or validating K3s on the control-plane node
joining worker nodes to the cluster
checking Kubernetes node readiness
detecting stale worker node records
installing required cluster-level prerequisites
running the OTP Relay deployment role after the cluster is ready
```

---

## Non-responsibilities

This layer does not:

```text
sync the Git repository
install GitHub Actions runners
create the worker VMs
own .env prompting logic
build frontend/app.js from frontend/app.jsx
generate frontend/help from docs/help
generate Grafana dashboard ConfigMaps
directly edit OTP Relay application source
replace the external NFS server
```

Repository sync is handled separately by:

```text
scripts/sync-repo.sh
```

Operator-controlled setup is started through:

```text
setup.sh
```

Application deployment logic is delegated to:

```text
install-otp-relay-k8s.sh
```

---

## Inventory model

The inventory is generated by the VM provisioner.

Expected generated file:

```text
automation/ansible/inventory.generated.ini
```

The inventory should describe:

```text
control-plane host
worker1
worker2
SSH user
SSH private key
worker IP addresses
```

The installer should not blindly trust stale inventory. Worker IPs in the generated inventory must match the Kubernetes node internal IPs after the cluster is joined.

If stale nodes exist, the cluster setup should either remove them during a fresh install/reset flow or stop with a clear diagnostic.

## Role layout

Typical role responsibilities:

```text
roles/k3s_server
  install and validate the K3s control-plane node

roles/k3s_agent
  join worker nodes to the K3s server

roles/node_labels
  apply Kubernetes node labels used by scheduling and placement rules

roles/nfs
  validate external NFS storage access when enabled

roles/otp_relay_deploy
  delegate OTP Relay workload deployment after the cluster is ready
```

The exact role set may evolve, but role boundaries should remain clear.

---

## Runtime state

The Ansible layer should not store OTP Relay runtime state inside the repository.

Runtime application data belongs on the configured persistent storage path, normally exposed to the application as:

```text
/app/data
```

This includes files such as:

```text
users.xlsx
admin_config.json
admin_auth.json
audit.log
wizard_progress.json
```

Shared OTP/admin runtime state is handled by Redis when Redis is enabled and required.

---

## Source of truth

The main operator input source is:

```text
.env
```

The Ansible layer should consume resolved values from `.env` or generated inventory. It should not introduce separate hardcoded production values.

Important values include:

```text
NAMESPACE
PORTAL_HOST
LOADBALANCER_IP
NFS_SERVER
NFS_EXPORT_PATH
REDIS_REQUIRED
APP_REPLICA_COUNT
MONITOR_NODE_SELECTOR
```

## Running the Ansible path

Normal users should start from the project root:

```bash
./setup.sh
```

The setup entrypoint decides whether the local-only installer path or the Ansible multi-node path should be used.

Direct Ansible execution is mainly for debugging.

## Validation checklist

After the Ansible layer completes, validate:

```bash
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -n otp-relay -o wide
sudo k3s kubectl get svc -n otp-relay -o wide
sudo k3s kubectl get ingress -n otp-relay -o wide
```

Expected high-level result:

```text
control-plane node Ready
worker1 Ready
worker2 Ready
OTP Relay app pods Running
monitor pod Running
Redis/Sentinel/HAProxy Running when enabled
Traefik LoadBalancer has the selected MetalLB IP
```

## Troubleshooting

If worker nodes do not join:

```text
check SSH reachability to each worker
check inventory.generated.ini worker IPs
check stale Kubernetes node records
check K3s token and server URL
check worker VM DNS and gateway access
```

If a worker install fails during K3s download, the role should use retry-safe curl behavior instead of a raw `curl | sh` pipe.

If the deployment role cannot find `.env` or the installer, verify that it is using the actual checkout path and not a hardcoded stale path.

---

## Design note

This Ansible layer is an extension beyond the simpler SCH Kubernetes baseline.

SCH’s baseline focuses on the OTP Relay application manifests and deployment workflow. This repository adds cluster provisioning and multi-node automation so the same application can run with stronger resilience:

```text
multi-node K3s
external NFS storage
Redis-backed shared state
worker placement
observability
operator-controlled setup
```

The Ansible layer should remain an infrastructure automation layer. It should not blur into application development or repository sync.
